# pi workbench: agent notes

Self-hosted web UI that drives the pi coding agent (`@earendil-works/pi-coding-agent`, pinned in the Dockerfile) through `pi --mode rpc`. See README.md for the architecture.

## Layout
- `server/`: Node ≥ 22.19 running TypeScript directly (type stripping, no build step). Imports must use the `.ts` extension, and only erasable syntax works (no enums, no parameter properties). Dependency: `ws`. Storage is `node:sqlite`.
- `web/`: React + Vite. It imports `../shared/` directly.
- `shared/transcript.ts`: the RPC-event → conversation reducer. **Both sides use it.** Change it in one place, never fork it.
- `shared/attach.ts`: the six pipeline places an installed skill can be **attached** to (`ATTACH_POINTS`, `AttachPoint`, `isAttachPoint`, `ATTACH_LABELS`). The page that sets them and the server that stores and reads them name them from here; `pipeline.ts` re-exports them, and the attach table lives beside them in `pipeline.ts` (issue #117).
- `shared/board.ts`: the phase → Board column map (`columnOf`) and the card shape behind `GET /api/board`. `Card.specCard` says whether a click on the card opens a row of ticket sub-cards (an unclaimed spec issue, a session with more than one ticket or one ticket that is not its own issue, a done spec with recorded sub-issues); `Card.subs` carries a done spec card's sub-issues. The web Board renders the row on every spec card: a started card's row is its session's tickets (state, live dot, waits-on, a link to the ticket's own run or its GitHub issue, and Solve / Retry / Mark done where they fit; a not-done ticket of a Done card shows "Not planned"), a done spec card's row is `Card.subs` with "Not planned" marks, and an unclaimed spec's row is its open sub-issues read from GitHub. A plain click on any other card opens the card-detail dialog, a modified click keeps its link. `boardCardActions` (the same gate the board card and the card detail use) says which whole-card actions a card's buttons carry: Approve while the card is in Review and Abandon until it is Done, on every session card including a direct one, and Stop, Retry and Answer on pipeline cards only — a direct card has no tickets to pause and no review or retro to re-run, and it answers a decision in the card detail. A card with no session (an unclaimed card, a done issue card) carries none. `isApproveMove` is the rule that a Review → Done drag is Approve, so the drag asks the Approve confirmation first. `cardStatus` derives `Card.status`: the card's one live status — `blocked` (a ticket of it is blocked), `waiting` (a decision or permission waits on the user), `stopped` (it carries a note, or its pi process died), `running` (a run of it works), or null for an idle card with no note, a Done card, and an unclaimed card — from its tickets, the session summary's `status`, and its `attention`. A live `stopped` alone is never a card status: the server says `stopped` whenever no pi process of the session runs, which is also the resting state of a run that finished, so a Review card waiting for Approve and a card after a server restart state nothing. `columnCounts(cards)` turns the cards into each column's count line: the number of cards plus one note per attention status it holds — the status and its count, not a sentence, so the view words it (`3 · 1 blocked · 1 waiting`); `running` and a null status add no note. The web Board renders a status icon on a card with a status (the word beside it for the three the user must look at) and the count line in the column header; `boardCardActions` reads none of that. Both sides use it too. The Board's kanzo-ported CSS is `web/src/board.css` (AGPL-3.0, see LICENSE).
- `pi-extension/workbench.ts`: loaded into every pi process via the generated `settings.json`. Imports of pi packages and `typebox` resolve to pi's own copies.
- `skills/`: workbench-bundled skills (asd-ste100, and the MIT `resolving-merge-conflicts`, which the pinned mattpocock commit lacks). The Dockerfile copies them into the image skills dir next to mattpocock's skills.
- The TypeSafe skill (`typesafe-ai/skills`, pinned in the Dockerfile) goes to `OPTIONAL_SKILLS_DIR`, which pi never scans. A session created with the TypeSafe box passes it with `--skill` and `PI_WORKBENCH_EXTRA_SKILLS`.

## Pipeline
- Every pi process is spawned with `--append-system-prompt`: user-facing explanations follow the asd-ste100 skill (Simplified Technical English). See `EXPLAIN_PROMPT` in `sessions.ts`.
- Phase transitions happen in `SessionManager.afterSettled`, after a run settles, never mid-run. The extension's pipeline tools only validate and acknowledge. The server reads their arguments from `tool_execution_start` and applies them on a successful `tool_execution_end`.
- Flow: setup → grill (`grill-with-docs`) → spec (`to-spec`) → tickets (`to-tickets`) → ready (paused; the card waits in Issues for Solve all) → implement (`tdd` per ticket) → review (`code-review`) → retro (`retro`, only when a ticket had a rescue) → pr (the PR is open; the card waits in Review for Approve) → done. Prompts are in `server/src/pipeline.ts`. pi only expands `/skill:name` when an argument follows on the same line; a unit test guards this.
- The **recorded setup state** (`repos.setup_state`, through `ADDED_COLUMNS`): `addRepo` (repos.ts) checks the setup marker on the default branch once, at add time, and records `set_up` or `not_set_up`. `repoSetupState` answers every later read from that record — a repo with a record gets no git check at all, and only a repo with no recorded state (a repo added before this change) gets one, which records what it found. Nothing but a landed setup push (issue #100, `recordSetUp`) writes the record, and a `set_up` is never downgraded, so a transient git failure cannot flag a set-up repo again; the price is that a repo that gained its skills some other way keeps `not_set_up` until it is removed and re-added. The record drives the repo view's `setup` state and, on top of it, whether a session starts with a setup run (issue #101, `needsSetupRun`, repos.ts). A repo recorded as set up starts in its planned phase and gets no marker check at all. A repo recorded as not set up starts in setup with no new check. Only a repo with no recorded state reads the marker off its fresh worktree (`worktreeNeedsSetup`), and that check runs once per worktree and records nothing: the add-time check and a landed setup push write the record. `server/test/setup-once.test.ts` drives the decision through a real session, and a `unit.test.ts` test counts the marker checks `needsSetupRun` makes. Whether a setup run *finished* still keys on the worktree: `afterSettled` releases the held task once the worktree carries the marker.
- The **setup session** (`repos.setup_session`, through `ADDED_COLUMNS`): adding or creating a repo whose recorded setup state is `not_set_up` starts one pipeline session titled "Set up agent skills" at once — `SessionManager.startSetupSession` (sessions.ts), with `setupOnly` in `CreateInput`, which sends the setup prompt and holds no task, so setup works on the board and its `ask_user` questions reach the user as decision cards. A repo recorded as `set_up` starts none, and `startSetupSession` returns null for it; a repo whose record names a session that still exists keeps that session instead of starting a second one. The repo records the session id in `createSession` as soon as its row exists — that record, not the return value, is what keeps a second add from making a second session — and the repo view carries it as `setupSession`; both repo routes go through `trackRepo` (main.ts), which reads the row again so its response carries it. Two adds of one repo at once share one run (`sessions.setupRuns`), as `create` does for two moves of one issue. A setup run that cannot start does not fail the repo add: for a `setupOnly` session `createSession` flags it with the reason instead of throwing. When its setup run settles with the marker committed, `isRepoSetupSession` holds it out of the grill fall-through, so it never reads as grilling a task, and `landSetupCommit` (sessions.ts) lands its commit on the repo's default branch (issue #100): `pushSetupCommit` (repos.ts) fetches the branch, pushes `HEAD:refs/heads/<base>`, and on a refusal fetches again, merges `origin/<base>` into the setup branch and pushes once more, aborting a merge that stops — it names the files git could not merge, and gives git's own words when the merge fails for another reason. No pull request, no Approve, and the setup prompt still tells the agent not to push. Only a commit that carries the marker can land: `pushSetupCommit` reads it with `git cat-file -e <ref>:SETUP_MARKER` on `HEAD` and on `origin/<base>`, so a marker the run wrote but never committed (in no ref) is a flagged failure rather than a success that landed nothing, and a default branch that already carries the marker lands as itself. When the commit lands, `recordSetUp` writes the repo's record as `set_up`, the worktree goes, the card goes to `done` with its attention cleared, and a `board` event goes out; a push that fails leaves the record at `not_set_up`, keeps the worktree, and flags the card with git's reason. A setup run the user stopped (`s.lastSettleAborted`) lands nothing: a half-done run would make the repo read as set up, so the card is flagged and a reply continues it. Abandon or archive clears the record (`clearSetupSession`), so a later add gets a fresh setup session.
- The **setup state the Repos page states** (`SessionManager.setupState`, sessions.ts, and the repo view's `setup` field: `set_up` | `in_progress` | `not_set_up`, `RepoSetupState` in repos.ts, issue #102): the record answers every read, `repoSetupState` records one marker check for a repo that has none, and a repo whose recorded setup session works now (`setupRunWorks`: the session is not archived, its phase is `setup`, and its live state says its setup run works, `Live.setupRunning`) reads as `in_progress`. A record naming a session that no longer works is not in progress, so the page states the repo as not set up. **Run setup** (`POST /api/repos/:owner/:name/setup` → `SessionManager.runSetup`) starts that session from the page: 409 for a repo recorded as `set_up`, 409 while the setup session works or its creation is in flight (`setupRuns`), and 409 naming the card when the record names a setup session that stopped — reply to that card, or Abandon it and Run setup starts a fresh one. `web/src/pages/Repos.tsx` states the three states and shows **Run setup** only for a repo stated as not set up.
- A **direct** session (`sessions.mode`, from a card's Grill or a task) runs no pipeline phases: its card sits in **Doing**, `POST /api/sessions/:id/pr` puts it in **Review**, and **Approve** (the Review → Done drag) or a Board load that finds its PR merged delivers it to **Done**. A backward drag of it is refused (409): it has no tickets to pause and no spec to rework. Every Review path applies to it: a conflict on its Approve takes the merge-run path below, and the card stays in **Review** for a second Approve. On the board its card carries Approve (in Review) and Abandon (until Done) only; Stop, Retry and Answer stay on pipeline cards. Its PR body is the user's own words, which carry no `Closes` line, so `delivered` closes the issues its refs name itself and records them in Done under the card. **Abandon** works on it exactly as on a pipeline card (its live run stops too — a direct card whose merge run works has no other way out of Review): its PR closes unmerged, its branch and worktree go, the session and its card are deleted, and a board event goes out; a Done card's merged PR is left alone, and the GitHub issues it named stay open.
- The tickets and split prompts carry `ticketSizeRule` (pipeline.ts): each ticket's whole `tdd` run must fit in about half of the Model settings context window, so a breakdown for a small-window model splits into smaller tickets. The to-tickets skill itself does not know the window size.
- The **Skills page** (`web/src/pages/Skills.tsx`, the sidebar entry **Skills**, the route `#/skills`; issue #116) is the library's page: it needs no session and no repo. Every Skill source is a row — URL, ref (or *default head*), subpath (or *the whole source*), the pinned commit, the installed size — with its installed skills under it (declared name, full description, file names). The **Add skill** form takes URL, ref and subpath, states the refusal inline in the form, and rereads `GET /api/skill-sources` after a successful add, so the page shows what the server installed. The page also states what a session can reach outside the library, read-only, from `GET /api/skills?typesafe=1`: the built-in optional TypeSafe skill, and the image skills. `listSkills` states a per-session extra skill as `Skill.source === "optional"`, never as an image skill, so the page names that row without guessing a name; `GET /api/skills` (no `typesafe`) answers without it. Attach points and an on/off switch are on each installed skill's row, and **Update** and **Remove** are on each source's row (issue #122).
- The **skill library** (`server/src/skill-library.ts`, the `skill_sources` and `installed_skills` tables, `config.installedSkillsDir`) owns the Skill sources the user added from git, the installed skills they brought, and the directory that holds them (issue #114). `GET /api/skill-sources` answers with every source — URL, ref, subpath, the commit it pinned, the installed size — and the skills under it (declared name, description, file names, its directory). `POST /api/skill-sources` adds one: a git URL (an absolute local path is refused with `file://` named as the way in, `file://` is accepted, and a value that reads as a git option is refused instead of run to git), an optional ref — a branch, a tag or a full commit hash, resolved with `git ls-remote`, and the install pins that one commit; with no ref the source's default head is pinned — and an optional subpath — the directory inside the source whose tree installs, named from the source's root, so an absolute path or a path that leaves the source is refused. The clone is shallow at the pinned commit, submodules stay off, and it runs with the global secret scope, so a private skill repo works with the saved token as a repo clone does. An add is all-or-nothing: the clone lands in a temporary directory inside the install directory, validates there — at least one `SKILL.md` with a name and a description, the kept tree under `SKILL_INSTALL_SIZE_LIMIT` (10 MB), no installed skill named like a pipeline skill — and only then moves into place, its git objects left behind; a refusal answers 400 with the reason and installs nothing, and no temporary clone stays. `PIPELINE_SKILLS` / `PIPELINE_SKILL_NAMES` (pipeline.ts) are the one name list the prompt builders' `/skill:` calls (pipeline.ts, and `SETUP_PROMPT` in sessions.ts) and the install check read (the unit test compares the two), so an install that would shadow the pipeline's own `tdd` is refused whole and the reason names the colliding skill. The install directory is in the data volume, so the rows and the tree survive a restart, and it is not a skills directory: `listSkills` never walks it and pi never scans it, so an installed skill reaches no run until it is attached (ADR 0004).
- **Update and Remove a Skill source** (issue #122): `installInPlace` (skill-library.ts) is the one install **Add skill** and **Update** share — clone the source shallowly at the commit its ref resolves to (`resolveCommit` reads it with `git ls-remote`; with no ref the source's default head, so an Update of a source that names no ref takes the head it has now), validate the clone where it lies with the same three checks an add runs, and only then move the tree into the source's place: a refusal installs nothing, leaves the tree that works where it was, and no temporary clone or stashed version stays on disk (`strayInstalls` in `server/test/skill-source-route.test.ts` counts them). `updateSkillSource` (skill-library.ts) is Update: it re-resolves the row's own ref, and an installed skill the new version carries too keeps its identifier, its switch and its attach points — a Ticket skill tag names an installed skill's identifier (issue #119), so new identifiers on every Update would orphan every card that carries one — while a skill the new version no longer carries goes, and `clearSkillTags` (db.ts) takes every ticket tag that named one of them off every ticket of every card, a Done card included. `keepIdentity` matches each carried name with one prior row, so a source that declares one name twice keeps two distinct installed skills, and what the library holds is read once the clone is validated, so a switch or an attach point the user changed while the clone ran is carried into the new version. `removeSkillSource` (skill-library.ts) is Remove: the source row and its installed skill rows go in one transaction (`deleteSkillSource`), then the source's directory, with the same tag clearing, and the answer names the source it removed and how many cards lost a tag. `POST /api/skill-sources/:sourceId/update` and `DELETE /api/skill-sources/:sourceId` (main.ts) go through `SessionManager.updateSkillSource` / `SessionManager.removeSkillSource` (sessions.ts), whose `announceTagChange` emits `emitSummary(…, true)` for each changed card and one `board` per repo, so an open card detail and Board state those tickets without the removed tags. A failed Update changes nothing that works: `recordSkillSourceFailure` stores `skill_sources.last_error` (through `ADDED_COLUMNS`), every library read answers it as `SkillSource.lastError`, the Skills page's source row states it beside the commit that still works, and an Update that gets through clears it. One Update runs per source at a time — `updating` (skill-library.ts) holds the source while its clone runs, so a second Update click and a Remove during that clone answer 409 instead of writing over the same place or leaving rows for a source that is gone. Add skill refuses a source the library already holds — one source per exact `(url, ref, subpath)`, 409 naming the pinned commit and Update as the way to take the new version — so two identical rows never hold two copies of one skill, and a second Add skill click while a clone of that source runs answers 409 too (`adding`, keyed on the `(url, ref, subpath)` the user named). In the web the source's row carries **Update** and **Remove** (`web/src/pages/Skills.tsx`), Remove behind a confirm that names the skills and the ticket tags it clears. `server/test/skill-source-route.test.ts` drives Update (the new version installed, the settings that survive, a setting changed while the clone runs, a named ref that has not moved, a source with no ref, a refused version that stays out, an unreachable source, two clicks that start one clone, a source that declares one name twice) and Remove (its rows, its directory, the tags it clears); `server/test/ticket-tags.test.ts` drives the tags Update and Remove take off the tickets, the Board card and the card detail.
- **Attach** (issue #117): each installed skill carries its on/off switch and its attach points in the `installed_skills` columns `enabled` and `attach` (a JSON list of the `shared/attach.ts` names, stored once each in that order; both columns go through `ADDED_COLUMNS`). `setSkillSettings` (skill-library.ts) stores the switch, the attach points, or both, and refuses a place the attach table does not know, so a typo never reads as a place; switching off is not un-attaching. `PATCH /api/skill-sources/:sourceId/skills/:skillId` is the route, and `GET /api/skill-sources` answers with both settings, so the Skills page's row (`web/src/pages/Skills.tsx`: the **On** checkbox and one checkbox per place, with the row stating which runs load the skill) reads them back after a reload. `attachPointOf` (pipeline.ts) is the one function that maps a run to the place it serves — a ticket run, a fix run and a solo ticket run are `implement`, a split card's held prompt and the tickets step are `tickets`, every run of a direct session is `direct`, a review run is `review`, and the setup, rescue, retro and merge runs are attached to nothing — read from `RunFacts` (`mode`, `phase`, `ticketRun`, `specialRun`), which `SessionManager.runFacts` builds from the session row and the run id. `spawn` reads the dirs once per run through `runSkillDirs` (`extraSkillDirs`, then `installedSkillDirs`, which reads `listAttachedSkills(db, place)`) and hands them to pi with `--skill` and `PI_WORKBENCH_EXTRA_SKILLS`, exactly as the TypeSafe skill does, so an installed skill reaches an agent only through its place. The dirs the live process carries are on `Live.skillDirs`; `SessionManager.realignRun` (at the top of `send`) restarts a conversation that now serves another place — the same pi session id, its history loaded back, so the card keeps its conversation — and a run that works is left alone: a change the user made reaches the next run of the place it names, never the run going now. `GET /api/skills?sessionId=` lists the session's repo, image and extra skills beside the installed skills of its current run, stated as `source: "installed"` (the 4th arg of `listSkills`). `server/test/skill-attach.test.ts` drives a real pi process through the session manager and reads the skills that process reports (`get_commands`): the attached place, a place it is not attached to, the setup run, and the off switch; `REVIEWASK` in mock-llm.ts makes the review run wait on one question, so its run can be read while it lives.
- An **attached pipeline place's prompt names its skills** (issue #118): `RunSkills` (`pipeline.ts` — `required` and `advertised`, each a `PromptSkill` name and description) is what a run's prompt carries about its place, and `skillsSection` → `withSkills` is the one place that renders it: a `## Skills attached to this pipeline place` block that names each required skill with "Load each one with the Skill tool before you write any code" and each advertised skill with "Load the ones that fit this work with the Skill tool", and that answers with nothing at all when the run has no attached skill, so an un-attached pipeline prompt is the same text as before. Every prompt builder takes the optional `RunSkills` last and appends the block after its own words, so the phase's own `/skill:` call stays the first line: `grillPrompt` and `reworkPrompt` are grill, `specPrompt` is spec, `ticketsPrompt` is tickets, `implementPrompt` and `fixPrompt` are implement, and `reviewPrompt` is review. The two held builders, `splitPrompt` (tickets) and `grillIssuePrompt` (grill), take no `RunSkills`: their text is stored before it is sent, so `withSkills` adds the block at the send. The setup, rescue, retro and merge prompts name no attached skill, as today. `SessionManager.promptSkills(id, runId)` (sessions.ts) builds the run's set from the same `attachPointOf(runFacts(…))` `spawn` reads: the place's attached skills are advertised, and the tags of the ticket the run belongs to are required (issue #120, the next bullet). A direct session is the exception: `promptSkills` answers with nothing for it, because the user writes that session's own prompt, and its attached skills stay reachable through the Skill tool. A held prompt is built without skills and gets the block at the moment it is sent or released (`withSkills` in `createSession` and in `releaseHeld`), so a card that waited for a setup run releases with the skills attached then, not at the click; the same holds for a pipeline session whose own prompt is already a skill call (the session form's ✦ Skills pick). `server/test/skill-attach.test.ts` reads the prompts the mock model actually received — pi expands `/skill:name` into the skill body, so the test asserts the phase's own `<skill name=…>` block still comes first, and that every skill the prompt names is one `get_commands` reports for that run; `LOADSKILL <name>` in mock-llm.ts makes the mock call the extension's Skill tool for that name.
- The **tickets step records each ticket's skill tags** (issue #119): the skills attached to the `tickets` place are the only names a ticket may be tagged with, and `Ticket skill tag` is the GLOSSARY word for one. `SessionManager.tagSkills(id, runId)` answers with `listAttachedSkills(db, "tickets")` when the run's `attachPointOf(runFacts(…))` is `tickets` and with nothing for every other run, and `spawn` passes those names to the extension as `PI_WORKBENCH_TICKET_SKILLS` — the tickets step is the only run given them. `skillsSection(skills, place)` and `withSkills(prompt, skills, place)` take the pipeline place, and only `tickets` adds the tag instruction after the skills block: each ticket gets a `skills` list of at most `TICKET_SKILL_TAG_LIMIT` (3) names, every ticket's tags are stated in the `ask_user` breakdown question so the user approves or corrects them, and `record_tickets` carries them. `ticketsPrompt` is the only builder that names `tickets`; a Split held prompt gets the instruction when it releases into that place, because `releaseHeld` and `createSession` pass the held prompt's phase to `withSkills`. With nothing attached to `tickets` no tag instruction is added at all, and the prompt is the text it always was; the setup, rescue, retro, merge, implement, review, grill, spec and direct prompts never ask for tags. Both sides check the call: `checkTickets` (pi-extension/workbench.ts) refuses a tag that is not a name or a ticket with more than the limit as `Not recorded: …`, so the agent fixes it and calls again, and a name no skill attached to `tickets` carries is **dropped** and named back in the tool result beside the names a ticket may use; `onPipelineTool` validates the same names with `validateTickets(args.tickets, names)` (`validateSkillTags` in pipeline.ts, the same cap) and drops them too, so a stale extension stores none. `skillTagIds` stores the kept names as the library's `installed_skills` identifiers in the new `tickets.skills` column (through `ADDED_COLUMNS`), and `toTicket` returns them as `Ticket.skills`, which every session ticket list carries (`GET /api/sessions`, `GET /api/sessions/:id`, and the session summary) and `web/src/types.ts` names; the card states them and sets them in #121, the next bullets. A card that never ran the tickets step records none: `validateTickets` applies no tag rule when no attached names were passed, so Solve, a Solve on a sub-issue, `ticketsFromSubIssues`, and every run of a direct session carry an empty list. `RunSkills.required` is filled by the ticket's tags of its own run (issue #120, the next bullet). `server/test/skill-attach.test.ts` drives a real pi process through the breakdown with its tags, the tags the card recorded, the dropped name with the usable names beside it, and the refused fourth tag.
- A **tagged ticket's run loads its tags** (issue #120): `ticketRunTagIds(tickets, runId)` (pipeline.ts) is the one rule that says which run ids are a ticket's own run — the ticket's `runId` (a ticket run, and a solo ticket run) or its `fixRunId` — and answers that ticket's stored tags; a rescue, review, retro, merge or plan run id answers nothing. `requiredTagSkills(tickets, runId, skillFor)` turns those ids into `PromptSkill`s through `installedSkill(db, tagId)`, in the ticket's own order, each name once, and drops a tag whose skill the library no longer holds. `SessionManager.promptSkills` answers `{ required, advertised }` from that, and `skillsSection` renders them apart: required with "Required. Load each one with the Skill tool before you write any code:", advertised with "Advertised. Load the ones that fit this work with the Skill tool:", the renderer dropping a name that is in both lists so a tagged skill is named once, as required. `installedSkillDirs` (its new `tagSkillDirs`) hands the run the tag's directory beside its place's attached dirs, so a tagged skill reaches its run whatever place it is attached to, and `runSkillDirs` → `spawn` pass them with `--skill` and `PI_WORKBENCH_EXTRA_SKILLS`. A direct session and the setup, rescue, retro and merge runs name no tag, and a ticket run with no tags and nothing attached keeps the prompt it always had (`skillsSection` answers `""` for nothing). `mock-llm.ts` reads the prompt's required list (`requiredSkillNames`) and makes a ticket run load each name with the extension's Skill tool as its first step, its other steps shifted by that one step; `NOBLOCK` in a task leaves the breakdown's third ticket unblocked, so one test can run every ticket of a tagged card. `server/test/skill-attach.test.ts` drives a real pi process through such a card: the solo run and the ticket run name their own tags as required and state the place's other skills apart, each run's first tool result is the Skill tool reading that tag's body, the tag's dir is on the run and on the session's own skill read, an untagged ticket of the same card and the card's review run name no tag as required, and the stored fix run id and rescue run id go through the same dirs.
- **A ticket's tags are editable on the card** (issue #121): `Ticket.skillTags` (pipeline.ts) is the name list beside `Ticket.skills`, read on every `SessionManager.tickets(id)` through `skillTagNames(tagIds, nameOf)` (pipeline.ts), which states each name once and names nothing for a tag whose skill the library no longer holds — so no view states a skill that is gone. `listInstalledSkills` and `listTaggableSkills` (skill-library.ts) are the two library reads: every installed skill, and the switched-on ones — the names a ticket may newly be tagged with, whatever pipeline place each skill is attached to, since a tag reaches its ticket's runs on its own. `SessionManager.setTicketTags(id, num, body)` is the one write, through `PATCH /api/sessions/:id/tickets/:num/skills`: it refuses a direct session and a Done card (409), a body that names no list and a fourth tag (400, with the cap named), applies the tickets step's `validateSkillTags` to the switched-on names **beside the names that ticket already carries** — so switching a skill off is never an un-tagging and a save never drops a carried tag behind the user — stores the kept names with `skillTagIds`, and answers with the stored ticket and the `dropped` names. It changes no run going now: `spawn` reads the skill dirs when a run starts, and `realignRun` holds while a run works. It emits `emitSummary(id)` and `board` for the repo, so an open card detail and Board state the same tags. `Card.ticketTags` (`TicketSkillTags` in shared/board.ts, built by `cardOf`, one entry per tagged ticket) is what a board read carries, and `canEditTicketTags(session)` is the one rule for whether a ticket's tags are editable: a pipeline card that is not Done. In the web, `TicketSkills` (web/src/pages/BoardDialogs.tsx) renders the tag chips and the **Skills** control in both the Board's ticket sub-card and the card detail's ticket row, and `TicketTags` is the checkbox dialog both open: it reads `/api/skill-sources`, keeps a carried switched-off skill checkable and states the tags a save will drop, and toasts every name the route dropped. `server/test/ticket-tags.test.ts` drives the route over HTTP — the stored ticket, the cap, the dropped names, the switch, the refusals — and the board card's tag names with the `board` event a change emits.
- The **solo ticket** (`sessions.solo_ticket`, through `ADDED_COLUMNS`): `POST /api/sessions/:id/tickets/:num/solve` (`SessionManager.solveTicket`) solves one ticket of a card in `ready` (Issues) — 409 for a card not in `ready`, a done or blocked ticket, or one with an open blocker (named in the message); a ticket a stopped run left `running` counts as ready and gets a fresh run. A sub-issue's Solve on an unclaimed spec card (`POST /api/repos/:owner/:name/issues/:number/tickets/:sub/solve`) creates the spec's session as the `tickets` start does, with the solo ticket set to the sub-issue's local number — 409 for a `:sub` that is not an open sub-issue of the spec, or whose open blockers inside the spec are not done (blockers outside the open set are dropped, as `ticketsFromSubIssues` does), and for a `:number` that is itself a sub-issue (as the move route refuses); on an un-setup repo, setup runs first, and then the solo ticket starts. While set, `runNext` pauses the card in `ready` when that ticket is done (its run, its fix run, or Mark done) instead of going on — every ticket done goes to the review as Solve all does — and a Retry re-runs the solo ticket, not the lowest ready one. Blocked and stopped solo outcomes keep the card in Doing with its attention, as today. Solve all, the pipeline's Stop, and backward moves clear the column.
- The **Issue queue** (`SessionManager.startQueue`, the `issue_queue` table in db.ts): the Board's Issues column header shows **Solve all issues** (`web/src/pages/Board.tsx`) while the column has cards and no queue runs for the repo, and the queue's status line with **Cancel** while one runs (issue #105). `POST /api/repos/:owner/:name/issues/queue` builds the snapshot the way the Board builds its cards — `queueNumbers` (shared/board.ts) lists every card Issues holds sorted by issue number: the unclaimed cards plus the session cards in `ready` — saves one row per number (`issueQueueSave`), and starts the first one. Each queued card makes its own move to Doing: an unclaimed plain issue is the `issue` start, an unclaimed spec issue is the `tickets` start, a session card in `ready` goes through `move(id, "doing")` (Solve all). The row in state `running` names the session the queue started; `releaseQueueStep` (from `finishPipeline`, `delivered`, `specHandClosed`, `abandon` and `archive`) marks that step `done` — `skipped` for a card the user dropped — and starts the next waiting number, so the queue moves when its card reaches Review with its PR open, and its rows go after the last one. A card the queue snapshotted but never started is a waiting row with no session: Abandon or archive of the card that held that number skips the row too (its issue numbers come from the card's refs, and only a not-done pipeline card claims an issue), so the queue never starts a fresh session for an issue the user dropped. `abandon` calls it only after its GitHub steps succeed, because a step that fails keeps the card, and the queue. `startQueuedCard` skips a number that is no longer a card in Issues: an issue another session claims now, an issue closed on GitHub, or a start the session refuses. The rows are the queue's whole state, so a server restart carries it; the queued card whose run the restart stopped still needs its usual resume (Retry, or a reply), and the queue waits on it. A queued card that is blocked, stopped, or waiting on the user's answer **pauses** the queue (issue #104): `issueQueueStep(…, "paused")` is a stored row (the `paused` state in `issue_queue`, and `IssueQueueState.paused`, so `GET /api/board` states the number the queue pauses on and the card stays in the queue's numbers), no next card starts, and `startNextQueuedCard` holds while any step is `running` or `paused` (`holdsQueue` in shared/board.ts is that pair, and `issueQueueState` reads it too) — a queue with a card it waits on is never advanced by a `startQueuedCard` claim or by a later card finishing. `SessionManager.pauseQueueStep` runs at every stuck point: `flag` (blocked ticket, stopped run, a stopped or failed solo outcome, a rescue or retro that cannot start, a pipeline transition that threw), and a pending request that waits on the user (`pauseForPending` at the request's registration and at the judgement sites where `waitsOnUser(req)` is true). `resumeQueueStep` clears the pause when the card works again: `answer` (the user answered a permission or a decision), and `send` (a reply, a Retry, a Skip, or any fresh run). The pause goes when the card leaves the queue: `pause` (a backward move out of Doing, or the pipeline's Stop) and `rework` release the step as `skipped`, so the next card starts and no second card is started for the card the user moved; Abandon and archive do the same. A card the queue started that reaches Review, or that the user Abandons or archives, releases the queue as before. A second click while rows exist is 409, and `sessions.queueRuns` holds the repo through a start so two clicks at once start one queue. Every step emits `board`. `SessionManager.queueState` is the `queue` field of `GET /api/board` (`issueQueueState` in shared/board.ts: the numbers still waiting, running or paused, the number the queue pauses on, and the `status` line `queueStatusLine` builds from the rows — the queue's place in the snapshot and the card it works on, pauses on, or is starting, e.g. `Queue 2 of 5 · on #12`). `liveQueueSteps` (shared/board.ts) is the one rule for the rows still in the queue (waiting, running, paused): `issueQueueState`'s numbers and Cancel's answer both read it. **Cancel** (issue #105, `POST /api/repos/:owner/:name/issues/queue/cancel` → `SessionManager.cancelQueue`) drops those rows: the Issues header shows **Solve all issues** again and a new queue is accepted, while the card that runs now keeps its run untouched — its own step is gone, so the `releaseQueueStep` it makes later finds no queue and starts no next card. It answers `{cancelled, working}`: the numbers of the cards it had not started, and the number of the card it leaves working. It is 409 when no queue runs — `issueQueueState`'s `running`, the same rule the header states — and while `startQueuedCard` starts one of its cards (`sessions.queueStarts`), because that card is already on its way. Both are a `board` event, so every open Board refetches; an open Board that is paused by a drag or an open dialog remembers the event and refetches when it is workable again.
- An **unclaimed card** (an open issue no session's `issue_ref`/`spec_ref` names; id `issue:<number>`, from `GitHub.listBoardIssues` — one GraphQL call, capped at the 100 most recently updated open issues, with each issue's open sub-issue count and parent) sits in **Issues**, plain and spec alike, and moves through `POST /api/repos/:owner/:name/issues/:number/move`. A sub-issue never is a card; a stale move of its number is refused (409) — the ticket-seed read in `github.ts` also returns whether the issue has a parent. The move picks the start: a spec (open ticket sub-issues) to Doing is `startFrom: tickets` (Solve all: the sub-issues are recorded as tickets and the session skips setup → grill → spec → tickets, starting at `implement`, or `setup` first on an un-setup repo); to To do it is `startFrom: spec` (the grill gets `reworkPrompt(spec URL)`, so the spec and tickets are updated in place). A plain issue (no open sub-issues, not itself a sub-issue) to Doing is `startFrom: issue` (Solve: the issue becomes the card's only ticket — its title, body, number as the tracker ref; the spec is the issue body, the spec ref the issue URL; it starts at `implement`, or `setup` first); to To do it is `startFrom: split` (Split: the session sits in `tickets` with `splitPrompt(issue URL)` — `/skill:to-tickets` on the issue — and waits for the user's approval; when `record_tickets` succeeds the card goes to ready/Issues; when setup finishes, `releaseHeld` releases a held prompt into the session's `held_phase` — `tickets` for a split, `grill` for a rework, a Grill or a task; it wraps the held prompt in the grill prompt only when that prompt is a bare task (`isSkillCall`), never a full skill call). All three starts set `issue_ref`, so the issue is claimed and the unclaimed card goes. A click on a plain card opens its card detail (title, body and link fetched through `GET /api/github/issues/:owner/:name/:number`), which shows the Solve, Grill and Split buttons and closes on a successful move or Grill; Grill is `POST /api/repos/:owner/:name/issues/:number/grill` and `startFrom: grill` (the held prompt is `grillIssuePrompt(seed)` — grill-with-docs on the issue's title, body and URL; the issue stays the session's origin, so the spec ref is null until `save_spec`, and a spec issue or a sub-issue number is refused with 409). A click on an unclaimed spec card toggles a row of its open ticket sub-issues as cards (each with a Solve — the sub-issue's solve route above — listed through `GET /api/repos/:owner/:name/issues/:number/tickets`), which collapses on the next click; a modified click opens the spec issue on GitHub. A new card, a landed setup card, an Approve that delivers a card, and an Abandon emit `board` on SessionManager, which goes to every browser as `{type: "wb_board", repoId}`; the Board refetches on it.
- A **board load's reconcile** (`SessionManager.reconcile`) is the one entry point for the GitHub checks on Board loads. `GET /api/board` reads the open issues and the PR state of each session that has a PR first (one read per PR number, reused for the badges; a state that cannot be read is null), adds the unclaimed spec cards to the `spec_watch` table (db.ts), and awaits reconcile. A card in phase `pr` whose PR state is `merged` and that is not in the `approving` or `resolving` sets is added to `approving` by reconcile itself, goes through `delivered` (the issues are recorded, the branch and worktree go, the phase is `done`), and leaves the set after; a card already in either set is left to that work. The **spec-closed rule** runs after it, for pipeline cards not in Done whose spec issue (spec ref, else issue ref) is not in the open-issue list, and is skipped for the load when that list could not be read: it skips a card the PR-merged rule delivered in this pass, a card in `pr` whose PR is merged, a card in `approving`/`resolving`, a card with a PR whose state could not be read (a merge whose `Closes` lines closed the spec is never taken for a hand close), and a plain issue card (its one ticket is its own issue). The batched read (`Delivery.issueStates`; the GitHub client reads many issues in one GraphQL call — one aliased `issue(number:)` field per number, numbers as declared Int variables, returning state, state reason, title, URL and sub-issues with their states — and retries one read per number when GitHub answers errors for a missing issue) confirms the state; a closed spec stops the card's runs, closes the spec's open sub-issues and the card's not-done ticket issues as `not planned` (`closeIssue` takes an optional state reason), removes the worktree, keeps the branch and the open PR, records the spec (no parent) and its sub-issues (the spec as parent) with the session id — not planned on the ones closed now or already closed as not planned on GitHub — sets the phase `done`, clears the solo ticket, and the note names the open PR and any failed step. A watched unstarted spec that is not open, claimed or done and that reads closed the same way closes its open sub-issues one at a time as not planned, records itself and its sub-issues in `issues_done` (no session id, so it is a card of its own in Done with the sub-issues in `Card.subs`), and leaves the watch list; an issue that no longer resolves leaves the watch list too. A ticket issue closed by hand changes nothing. Reconcile runs at most once at a time per repo: an overlapping Board load waits for the run in progress and gets its result (`moved`, and the numbers the run recorded as done). When a card moved, reconcile emits `board` for the repo (every open Board refetches), removes the done numbers from the spec watch list, and the route lists the sessions again before it builds the cards. The done numbers also drop out of the same response's unclaimed cards (`unclaimedCards`' 4th arg); a spec issue a session claims leaves the watch list in `create`.
- The **issues a merged card closes** (the ticket issues, the spec issue and the origin issue) are recorded in Done: `SessionManager.delivered` records them in the `issues_done` table (db.ts, `recordIssueDone`/`doneIssuesOf`) with a title and URL read through `Delivery.issueInfo` (a fallback of `Issue #n` when the issue cannot be read), the card's session id, and the spec issue as `parent` for a ticket issue. The board groups them (`doneIssueCards` in shared/board.ts, which takes the ids of every session listed for the repo, before the Done cut): an issue whose closing session is on the board sits in that card's row, a done spec with recorded sub-issues is a card of its own with them in `Card.subs`, and records from before the columns (no session, no parent) stay flat cards beside the merged cards, newest first (`Card.doneAt`). A closed foreign issue is recorded on its own tracked repo, and a `board` event goes out for it.
- Each ticket runs under its own pi session id (`<session>-t<num>-<stamp>`), stored on the ticket row, and the review under `sessions.review_run`. A stuck ticket's rescue run (`<session>-t<num>-rescue-<stamp>`, `tickets.rescue_run_id`) and fix run (`-fix-`, `tickets.fix_run_id`) and the retro (`<session>-retro-<stamp>`, `sessions.retro_run`) get their own ids too. A conflict on Approve that `git merge origin/<base>` cannot settle gets a merge run (`<session>-merge-<stamp>`, `sessions.merge_run`) that ends with `finish_merge`; the server pushes it and the phase stays `pr`. `sessions.active_run` says which run is live. A run switch emits `wb_run`, and the browser re-subscribes to get the new snapshot. Switch runs *before* announcing a phase that implies the switch.
- The stop rule (`server/src/stop-rule.ts`) watches ticket, rescue, fix, and retro runs only. `SessionManager` aborts a run when a condition fires; `afterTicketRun` and `afterRetroRun` pick the outcome. Rescue and retro runs (ids matching `-rescue-`/`-retro-`) call the Reviewer model through the localhost proxy in `rescue-proxy.ts` (ADR 0003); the Reviewer key never enters a pi process.
- `server/test/mock-llm.ts` scripts each phase by step. Keep `test/pipeline-e2e.test.ts` passing when you change prompts, tools, or transitions.
- New columns go through `ADDED_COLUMNS` in `db.ts`, so older databases migrate on open.

## Rules
- The extension and the server share a protocol: a dialog title that is a JSON `{"wb": "permission" | "decision", ...}` envelope. Change both together, and keep `server/test/e2e.test.ts` passing.
- Never return secret values from the API, and never log them. `SecretStore.envFor` is the only decrypting path to pi. The master key must stay out of child environments: `processEnv` and `git()` strip it.
- The UI has no login. Every new write route goes through the JSON + Origin + Host check in `server/src/http.ts`. Don't add GET routes with side effects. The exceptions are `GET /api/board`: its load runs the repo's reconcile (see the pipeline section), which can deliver a hand-merged PR and stop a hand-closed spec's card; and `GET /api/repos`: `SessionManager.setupState` runs the one git check for a repo with no recorded state and records what it found.
- Settings in the db are the source of truth. `writePiConfig` regenerates pi's agent dir from them, so don't hand-edit `/data/pi-agent`.
- Read pi's stdout with the LF splitter in `rpc.ts`, not `readline`: `readline` also splits on U+2028/2029.
