# pi workbench: agent notes

Self-hosted web UI that drives the pi coding agent (`@earendil-works/pi-coding-agent`, pinned in the Dockerfile) through `pi --mode rpc`. See README.md for the architecture.

## Layout
- `server/`: Node ≥ 22.19 running TypeScript directly (type stripping, no build step). Imports must use the `.ts` extension, and only erasable syntax works (no enums, no parameter properties). Dependency: `ws`. Storage is `node:sqlite`.
- `web/`: React + Vite. It imports `../shared/` directly.
- `shared/transcript.ts`: the RPC-event → conversation reducer. **Both sides use it.** Change it in one place, never fork it.
- `shared/board.ts`: the phase → Board column map (`columnOf`) and the card shape behind `GET /api/board`. `Card.specCard` says whether a click on the card opens a row of ticket sub-cards (an unclaimed spec issue, a session with more than one ticket or one ticket that is not its own issue, a done spec with recorded sub-issues); `Card.subs` carries a done spec card's sub-issues. The web Board renders the row on every spec card: a started card's row is its session's tickets (state, live dot, waits-on, a link to the ticket's own run or its GitHub issue, and Solve / Retry / Mark done where they fit; a not-done ticket of a Done card shows "Not planned"), a done spec card's row is `Card.subs` with "Not planned" marks, and an unclaimed spec's row is its open sub-issues read from GitHub. A plain click on any other card opens the card-detail dialog, a modified click keeps its link. `boardCardActions` (the same gate the board card and the card detail use) says which whole-card actions a card's buttons carry: Approve while the card is in Review and Abandon until it is Done, on every session card including a direct one, and Stop, Retry and Answer on pipeline cards only — a direct card has no tickets to pause and no review or retro to re-run, and it answers a decision in the card detail. A card with no session (an unclaimed card, a done issue card) carries none. `isApproveMove` is the rule that a Review → Done drag is Approve, so the drag asks the Approve confirmation first. Both sides use it too. The Board's kanzo-ported CSS is `web/src/board.css` (AGPL-3.0, see LICENSE).
- `pi-extension/workbench.ts`: loaded into every pi process via the generated `settings.json`. Imports of pi packages and `typebox` resolve to pi's own copies.
- `skills/`: workbench-bundled skills (asd-ste100, and the MIT `resolving-merge-conflicts`, which the pinned mattpocock commit lacks). The Dockerfile copies them into the image skills dir next to mattpocock's skills.
- The TypeSafe skill (`typesafe-ai/skills`, pinned in the Dockerfile) goes to `OPTIONAL_SKILLS_DIR`, which pi never scans. A session created with the TypeSafe box passes it with `--skill` and `PI_WORKBENCH_EXTRA_SKILLS`.

## Pipeline
- Every pi process is spawned with `--append-system-prompt`: user-facing explanations follow the asd-ste100 skill (Simplified Technical English). See `EXPLAIN_PROMPT` in `sessions.ts`.
- Phase transitions happen in `SessionManager.afterSettled`, after a run settles, never mid-run. The extension's pipeline tools only validate and acknowledge. The server reads their arguments from `tool_execution_start` and applies them on a successful `tool_execution_end`.
- Flow: setup → grill (`grill-with-docs`) → spec (`to-spec`) → tickets (`to-tickets`) → ready (paused; the card waits in Issues for Solve all) → implement (`tdd` per ticket) → review (`code-review`) → retro (`retro`, only when a ticket had a rescue) → pr (the PR is open; the card waits in Review for Approve) → done. Prompts are in `server/src/pipeline.ts`. pi only expands `/skill:name` when an argument follows on the same line; a unit test guards this.
- A **direct** session (`sessions.mode`, from a card's Grill or a task) runs no pipeline phases: its card sits in **Doing**, `POST /api/sessions/:id/pr` puts it in **Review**, and **Approve** (the Review → Done drag) or a Board load that finds its PR merged delivers it to **Done**. A backward drag of it is refused (409): it has no tickets to pause and no spec to rework. Every Review path applies to it: a conflict on its Approve takes the merge-run path below, and the card stays in **Review** for a second Approve. On the board its card carries Approve (in Review) and Abandon (until Done) only; Stop, Retry and Answer stay on pipeline cards. Its PR body is the user's own words, which carry no `Closes` line, so `delivered` closes the issues its refs name itself and records them in Done under the card. **Abandon** works on it exactly as on a pipeline card (its live run stops too — a direct card whose merge run works has no other way out of Review): its PR closes unmerged, its branch and worktree go, the session and its card are deleted, and a board event goes out; a Done card's merged PR is left alone, and the GitHub issues it named stay open.
- The tickets and split prompts carry `ticketSizeRule` (pipeline.ts): each ticket's whole `tdd` run must fit in about half of the Model settings context window, so a breakdown for a small-window model splits into smaller tickets. The to-tickets skill itself does not know the window size.
- The **solo ticket** (`sessions.solo_ticket`, through `ADDED_COLUMNS`): `POST /api/sessions/:id/tickets/:num/solve` (`SessionManager.solveTicket`) solves one ticket of a card in `ready` (Issues) — 409 for a card not in `ready`, a done or blocked ticket, or one with an open blocker (named in the message); a ticket a stopped run left `running` counts as ready and gets a fresh run. A sub-issue's Solve on an unclaimed spec card (`POST /api/repos/:owner/:name/issues/:number/tickets/:sub/solve`) creates the spec's session as the `tickets` start does, with the solo ticket set to the sub-issue's local number — 409 for a `:sub` that is not an open sub-issue of the spec, or whose open blockers inside the spec are not done (blockers outside the open set are dropped, as `ticketsFromSubIssues` does), and for a `:number` that is itself a sub-issue (as the move route refuses); on an un-setup repo, setup runs first, and then the solo ticket starts. While set, `runNext` pauses the card in `ready` when that ticket is done (its run, its fix run, or Mark done) instead of going on — every ticket done goes to the review as Solve all does — and a Retry re-runs the solo ticket, not the lowest ready one. Blocked and stopped solo outcomes keep the card in Doing with its attention, as today. Solve all, the pipeline's Stop, and backward moves clear the column.
- An **unclaimed card** (an open issue no session's `issue_ref`/`spec_ref` names; id `issue:<number>`, from `GitHub.listBoardIssues` — one GraphQL call, capped at the 100 most recently updated open issues, with each issue's open sub-issue count and parent) sits in **Issues**, plain and spec alike, and moves through `POST /api/repos/:owner/:name/issues/:number/move`. A sub-issue never is a card; a stale move of its number is refused (409) — the ticket-seed read in `github.ts` also returns whether the issue has a parent. The move picks the start: a spec (open ticket sub-issues) to Doing is `startFrom: tickets` (Solve all: the sub-issues are recorded as tickets and the session skips setup → grill → spec → tickets, starting at `implement`, or `setup` first on an un-setup repo); to To do it is `startFrom: spec` (the grill gets `reworkPrompt(spec URL)`, so the spec and tickets are updated in place). A plain issue (no open sub-issues, not itself a sub-issue) to Doing is `startFrom: issue` (Solve: the issue becomes the card's only ticket — its title, body, number as the tracker ref; the spec is the issue body, the spec ref the issue URL; it starts at `implement`, or `setup` first); to To do it is `startFrom: split` (Split: the session sits in `tickets` with `splitPrompt(issue URL)` — `/skill:to-tickets` on the issue — and waits for the user's approval; when `record_tickets` succeeds the card goes to ready/Issues; when setup finishes, `releaseHeld` releases a held prompt into the session's `held_phase` — `tickets` for a split, `grill` for a rework, a Grill or a task; it wraps the held prompt in the grill prompt only when that prompt is a bare task (`isSkillCall`), never a full skill call). All three starts set `issue_ref`, so the issue is claimed and the unclaimed card goes. A click on a plain card opens its card detail (title, body and link fetched through `GET /api/github/issues/:owner/:name/:number`), which shows the Solve, Grill and Split buttons and closes on a successful move or Grill; Grill is `POST /api/repos/:owner/:name/issues/:number/grill` and `startFrom: grill` (the held prompt is `grillIssuePrompt(seed)` — grill-with-docs on the issue's title, body and URL; the issue stays the session's origin, so the spec ref is null until `save_spec`, and a spec issue or a sub-issue number is refused with 409). A click on an unclaimed spec card toggles a row of its open ticket sub-issues as cards (each with a Solve — the sub-issue's solve route above — listed through `GET /api/repos/:owner/:name/issues/:number/tickets`), which collapses on the next click; a modified click opens the spec issue on GitHub. A new card, an Approve that delivers a card, and an Abandon emit `board` on SessionManager, which goes to every browser as `{type: "wb_board", repoId}`; the Board refetches on it.
- A **board load's reconcile** (`SessionManager.reconcile`) is the one entry point for the GitHub checks on Board loads. `GET /api/board` reads the open issues and the PR state of each session that has a PR first (one read per PR number, reused for the badges; a state that cannot be read is null), adds the unclaimed spec cards to the `spec_watch` table (db.ts), and awaits reconcile. A card in phase `pr` whose PR state is `merged` and that is not in the `approving` or `resolving` sets is added to `approving` by reconcile itself, goes through `delivered` (the issues are recorded, the branch and worktree go, the phase is `done`), and leaves the set after; a card already in either set is left to that work. The **spec-closed rule** runs after it, for pipeline cards not in Done whose spec issue (spec ref, else issue ref) is not in the open-issue list, and is skipped for the load when that list could not be read: it skips a card the PR-merged rule delivered in this pass, a card in `pr` whose PR is merged, a card in `approving`/`resolving`, a card with a PR whose state could not be read (a merge whose `Closes` lines closed the spec is never taken for a hand close), and a plain issue card (its one ticket is its own issue). The batched read (`Delivery.issueStates`; the GitHub client reads many issues in one GraphQL call — one aliased `issue(number:)` field per number, numbers as declared Int variables, returning state, state reason, title, URL and sub-issues with their states — and retries one read per number when GitHub answers errors for a missing issue) confirms the state; a closed spec stops the card's runs, closes the spec's open sub-issues and the card's not-done ticket issues as `not planned` (`closeIssue` takes an optional state reason), removes the worktree, keeps the branch and the open PR, records the spec (no parent) and its sub-issues (the spec as parent) with the session id — not planned on the ones closed now or already closed as not planned on GitHub — sets the phase `done`, clears the solo ticket, and the note names the open PR and any failed step. A watched unstarted spec that is not open, claimed or done and that reads closed the same way closes its open sub-issues one at a time as not planned, records itself and its sub-issues in `issues_done` (no session id, so it is a card of its own in Done with the sub-issues in `Card.subs`), and leaves the watch list; an issue that no longer resolves leaves the watch list too. A ticket issue closed by hand changes nothing. Reconcile runs at most once at a time per repo: an overlapping Board load waits for the run in progress and gets its result (`moved`, and the numbers the run recorded as done). When a card moved, reconcile emits `board` for the repo (every open Board refetches), removes the done numbers from the spec watch list, and the route lists the sessions again before it builds the cards. The done numbers also drop out of the same response's unclaimed cards (`unclaimedCards`' 4th arg); a spec issue a session claims leaves the watch list in `create`.
- The **issues a merged card closes** (the ticket issues, the spec issue and the origin issue) are recorded in Done: `SessionManager.delivered` records them in the `issues_done` table (db.ts, `recordIssueDone`/`doneIssuesOf`) with a title and URL read through `Delivery.issueInfo` (a fallback of `Issue #n` when the issue cannot be read), the card's session id, and the spec issue as `parent` for a ticket issue. The board groups them (`doneIssueCards` in shared/board.ts, which takes the ids of every session listed for the repo, before the Done cut): an issue whose closing session is on the board sits in that card's row, a done spec with recorded sub-issues is a card of its own with them in `Card.subs`, and records from before the columns (no session, no parent) stay flat cards beside the merged cards, newest first (`Card.doneAt`). A closed foreign issue is recorded on its own tracked repo, and a `board` event goes out for it.
- Each ticket runs under its own pi session id (`<session>-t<num>-<stamp>`), stored on the ticket row, and the review under `sessions.review_run`. A stuck ticket's rescue run (`<session>-t<num>-rescue-<stamp>`, `tickets.rescue_run_id`) and fix run (`-fix-`, `tickets.fix_run_id`) and the retro (`<session>-retro-<stamp>`, `sessions.retro_run`) get their own ids too. A conflict on Approve that `git merge origin/<base>` cannot settle gets a merge run (`<session>-merge-<stamp>`, `sessions.merge_run`) that ends with `finish_merge`; the server pushes it and the phase stays `pr`. `sessions.active_run` says which run is live. A run switch emits `wb_run`, and the browser re-subscribes to get the new snapshot. Switch runs *before* announcing a phase that implies the switch.
- The stop rule (`server/src/stop-rule.ts`) watches ticket, rescue, fix, and retro runs only. `SessionManager` aborts a run when a condition fires; `afterTicketRun` and `afterRetroRun` pick the outcome. Rescue and retro runs (ids matching `-rescue-`/`-retro-`) call the Reviewer model through the localhost proxy in `rescue-proxy.ts` (ADR 0003); the Reviewer key never enters a pi process.
- `server/test/mock-llm.ts` scripts each phase by step. Keep `test/pipeline-e2e.test.ts` passing when you change prompts, tools, or transitions.
- New columns go through `ADDED_COLUMNS` in `db.ts`, so older databases migrate on open.

## Rules
- The extension and the server share a protocol: a dialog title that is a JSON `{"wb": "permission" | "decision", ...}` envelope. Change both together, and keep `server/test/e2e.test.ts` passing.
- Never return secret values from the API, and never log them. `SecretStore.envFor` is the only decrypting path to pi. The master key must stay out of child environments: `processEnv` and `git()` strip it.
- The UI has no login. Every new write route goes through the JSON + Origin + Host check in `server/src/http.ts`. Don't add GET routes with side effects — the one exception is `GET /api/board`: its load runs the repo's reconcile (see the pipeline section), which can deliver a hand-merged PR and stop a hand-closed spec's card.
- Settings in the db are the source of truth. `writePiConfig` regenerates pi's agent dir from them, so don't hand-edit `/data/pi-agent`.
- Read pi's stdout with the LF splitter in `rpc.ts`, not `readline`: `readline` also splits on U+2028/2029.

## Checks
- `cd server && npm test`: unit tests, plus GitHub flow against `test/mock-github.ts`, plus e2e against a real pi process and `test/mock-llm.ts`. The e2e tests skip when `pi` isn't on PATH; set `PI_BIN` to point at one.
- `cd web && npm run build`: `tsc --noEmit` and the Vite build.
