# Rescue and retro runs call the frontier model through a localhost proxy

A rescue run diagnoses a stuck ticket with the Reviewer's model, and a retro run reviews the rescued tickets at the end of a spec. Both run as pi agents in the session's worktree, and calling the model directly from the agent would need the Reviewer's API key in the pi process's environment. From there the rescue agent itself — and any repo test or script it runs — can read it with `process.env` and send it out over HTTP; the approval rules gate only `curl` and `wget`, so a plain node or python script would leak the key. The proxy instead listens on `127.0.0.1` only, on an ephemeral port, separate from the UI port. Each rescue or retro run gets its own random token in that run's environment; a second provider in the generated `models.json` (`workbench-rescue`) points at the proxy and reads the key from that token environment variable. The proxy adds the Reviewer's real key in the provider's header, forwards the request to the Reviewer's URL, streams the response back, refuses requests when the URL's origin does not match the key's saved origin, and revokes the token when the run exits. It logs neither the key nor the token.

**Considered alternatives**: the key in the rescue run's environment (the rescue agent and any repo test it runs can read `process.env` and send it out over HTTP; the approval rules gate only `curl` and `wget`); a token per key rather than per run (an old or leaked token would keep working until rotated).

**Consequences**: extends ADR 0002 — the Reviewer key stays in `SecretStore` and never enters a pi process, now including rescue and retro runs; the server runs a second HTTP listener, but it binds to loopback only; `models.json` gains a `workbench-rescue` provider that no run reaches without a live token.
