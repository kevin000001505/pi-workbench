# Installed skills attach to pipeline places and load through the Skill tool

The pipeline names one skill per phase (`/skill:grill-with-docs`, `/skill:to-spec`, `/skill:to-tickets`, `/skill:tdd`, `/skill:code-review`), and the workbench passes every skill in the scanned skills directory to every run. A skill for one region of knowledge, such as frontend design, does not fit that shape: it sits in front of a run that fixes a SQL bug, and a small local model can spend its context on it. Installed skills therefore stay out of the scanned skills directory. Each one is **attached** to the pipeline places you name — grill, spec, tickets, implement, review, or a direct session — and the workbench passes that skill's directory only to the runs of those places, with `--skill` and the extra-skills environment the extension reads. The phase prompt names the attached skills and tells the agent to load them with the extension's `Skill` tool. A **ticket skill tag** makes one of them required for one ticket, and the tickets step proposes the tags so you approve them before any run starts.

**Considered alternatives**: put installed skills in the scanned skills directory, as the image skills are (every run of every session pays their descriptions, and the pipeline cannot tell a frontend skill from a database skill); embed the full skill text in the phase prompt (deterministic, but it pays the tokens on every run, needed or not — and pi expands only a prompt that starts with `/skill:`, so only one skill call expands anyway); per-session opt-in at session start, as the TypeSafe skill does (you choose before you know what the tickets are, and skill choices then live in two places); description-based routing with no attach and no tag (invisible to you, unauditable, and weak on a small local model).

**Consequences**: the skills a run can reach come from three sources — image, repo, installed — through one mechanism, and installed skills add no name to the scanned directory; an install that carries a skill name a pipeline prompt already names is refused, because a shadowed `tdd` silently changes how every ticket run behaves; a run's required skills come from stored ticket tags, so a tag is something you can read and correct on the card before the run starts; a skill's instructions enter a run only when the agent loads them, so a tagged run is not guaranteed to load them.
